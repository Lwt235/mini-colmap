### Dino 边界案例

原始完整 363 图运行 `ui_20261018_163545_713ebb` 注册 **102/363** 台相机、778 点，平均重投影误差约 1.139 px。其初始匹配分量只覆盖 132 张照片，其余 231 张没有到初始地图的连接。

使用 `configs/dino_sfm.json` 的修复配置，将图像对准入设为 20、初始化仍为 30，并保留一致子轨迹。在同一份 SIFT/F-RANSAC 缓存上重新运行完整候选初始化、注册和三角化，得到 `dino363_repaired_cached_52058b`：

| 指标 | 原始运行 | 修复后缓存建图重放 |
| --- | ---: | ---: |
| 注册图像 | 102 / 363（28.1%） | 321 / 363（88.4%） |
| 三维点 / 观测 | 778 / 4,680 | 3,036 / 25,716 |
| 平均重投影误差 | 1.139 px | 1.162 px |
| 正深度比例 | 1.0 | 1.0 |
| 共同 101 图的旋转误差中位数 | 2.755° | 1.969° |

旋转误差先在同一组 101 台共同相机上分别拟合全局旋转规范，再与官方 R 比较，参考位姿只用于评价。新结果新增注册 220 张，原已注册的 18 号本次未通过检查；仍有 42 张未注册，其中 13 张位于初始匹配分量之外。PnP 的 15 点要求、3 px 重投影门槛和视差/正深度筛选沿用原阈值。

修复验收复用特征和 F 匹配缓存，约 135 s 的计时覆盖候选初始化、注册和三角化；原始完整流水线还包含照片前端，两种耗时分别按各自覆盖阶段报告。TempleRing 47 图默认配置的完整重放模型与旧模型逐项相同。原始实验保留，下表既有 Dino 3DGS 实验使用旧地图的 102 台相机，训练与验证划分均取自这 102 张已注册照片。

## 新视图合成

| 实验 | 输入 / 划分 | 步数与评价尺寸 | 全部验证视角 PSNR |
| --- | --- | --- | ---: |
| TempleRing NeRF | 47 图，36 训练 / 11 验证 | 6,000 步，160×120 | 24.17 dB |
| TempleRing 3DGS | 47 图，36 / 11，最终 6,726 高斯 | 5,000 步，160×120 | 31.83 dB |
| Dino 3DGS | SfM 已注册的 102 图，77 / 25，最终 2,623 高斯 | 30,000 步，80×60 | 29.00 dB |

TempleRing NeRF 配置为 `configs/nerf_temple_quality.json`，核心参数为 8 层主干、256 隐藏维数、黑背景、跨图射线采样及分层采样。TempleRing 3DGS 使用 gsplat/CUDA、学习率 0.001、SH3、增密间隔 100 和 100,000 容量预算，最终实际数量为 6,726。Dino 的场景、图像尺寸与有效视图数均与 TempleRing 不同，各分数按各自条件解读。

PSNR 先对各等尺寸验证视图的 MSE 取均值，再按 `−10·log10(各等尺寸验证视图的平均 MSE)` 换算；逐视图 PSNR 均值与训练 loss 各有独立定义。中途预览可能只对应一张验证图，以指标的 `psnr_scope` 为准。留出范围为外观监督，位姿由全图 SfM 估计；评价覆盖共享几何条件下的场景内留出视角合成。

NeRF 已恢复主体轮廓，细纹理仍偏软；3DGS 的 31.83 dB 对应本场景的低分辨率实验。比较模型时固定验证图像、评价分辨率、背景和采样/渲染口径。

## 3DGS 训练策略消融（2026-10-19）

完成 36 项双种子策略筛选、12 项固定高斯数量损失对照，以及 2 项原图确认，共 **50 项真实 CUDA 训练**。输入为 Temple47、Temple312 和 Dino321，只有两种物体身份。候选仅按 dev 选择；固定 SfM 地图来自全图，test 为不参与训练损失的留出视角。

原图确认使用 Temple312 的同一份 19,648 点地图、297 训练 / 8 dev / 7 test、640×480、10,000 步、种子 0、100,000 高斯预算：

| 策略 | test PSNR / dB | test SSIM | 实际高斯数 | 训练 / s | 峰值 allocated / MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 旧基线 | 26.45 | 0.7870 | 24,527 | 268.4 | 90.5 |
| 组合策略 | 36.02 | 0.9546 | 100,000 | 559.8 | 293.7 |

测试 PSNR 提高 **9.57 dB**，同时训练耗时约为 2.09 倍，实际容量约为 4.08 倍。各变体共享容量上限，实际高斯数如表所列。固定容量控制中，L1＋SSIM 单独带来约 0.47–0.73 dB 的测试增益；完整组合还包含学习率与密度策略变化，整体收益按组合实验报告。分组学习率在三个输入组中均有效；仅保留 Adam 状态时，三个输入组的测试 PSNR 均低于旧基线，单独使用自适应密度策略的均值也均低于旧基线。

完整矩阵、负结果、源码指纹、评价定义、原图对照和复现方法见 [优化与消融说明](3dgs-optimization-ablation.md)。原图确认覆盖单种子、10,000 步条件，基线与候选在相同原图条件下比较。

## 3DGS 实时链路

新增原图确认模型使用 RTX 4060 Laptop、SH3、1280×720、JPEG85，headless Edge 预热 10 s、持续测量 60 s：

| 原图模型 | 高斯数 | 浏览器新图像提交 / FPS | 请求至提交 P95 / ms |
| --- | ---: | ---: | ---: |
| 同配置旧基线 | 24,527 | 53.84 | 36.4 |
| 优化组合 | 100,000 | 54.22 | 29.8 |

两者在这次测量中的吞吐接近，各模型的帧率与延迟按表中单次测量结果报告。新模型同时通过旋转、平移、缩放、相机对齐、窗口缩放与重连检查。逐帧记录见本轮 [消融报告](3dgs-optimization-ablation.md)。

较早保存的性能记录使用 RTX 4060 Laptop、6,570 个高斯、SH3、1280×720、JPEG quality=85。预热 10 s，测量 60 s；Python 客户端与 Edge 分别执行：

| 测量 | 数值 |
| --- | ---: |
| Edge 新渲染图像 RAF 提交速率 | 91.13 帧/秒 |
| Edge 请求到图像提交延迟 P95 | 18.30 ms |
| Edge 测试期间 GPU 渲染均值 | 4.53 ms |
| Python 客户端接收并 CPU 解码吞吐 | 78.09 帧/秒 |

浏览器记录来自 headless Edge 生产组件中的新图像提交，覆盖请求、GPU、读回、编码、传输、解码与等待 RAF；计数对象为有新渲染图像的 RAF 提交。Python 客户端额外使用 OpenCV CPU 解码，吞吐按接收并完成 CPU 解码的图像数统计。

该记录对应旧的 6,570 高斯模型，前表的画质实验使用 6,726 高斯模型。配置允许的容量上限为 500 万，本次 Windows Edge 实测模型为 6,570 高斯；百万高斯测量来自下节的 Linux 协议。

### Linux 百万高斯与受控网络

另一组历史对照使用 RTX A6000、100 万高斯、SH3、1280×720、JPEG95，模型与相机保持不变，预热 3 秒、测量 15 秒：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| GPU 渲染均值 | 9.65 ms | 3.91 ms |
| 顺序 WebSocket 接收＋CPU JPEG 解码 | 45.66 帧/s | 59.11 帧/s |

独立融合路径保持完整模型，在三个真实相机上的浮点 RGB 最大绝对差为 `5.96e-7`。上述吞吐统计 Linux 环境中的顺序 WebSocket 接收与 CPU JPEG 解码。

受控 Chromium 网络实验在同一优化服务端、两请求流水线下对比交互降质开关：80 ms RTT / 8 Mbps 下载时，浏览器新图像显示速率从 **3.96 → 14.37 帧/s**，帧间隔 P95 从 **368.2 → 116.9 ms**，平均图像字节数从 180,332 降至 40,254；停止交互后恢复最终质量。结果反映上述受控带宽与时延条件下的画质—吞吐折中。聚合时延、相机一致性及协议见 [实时证据](../reports/benchmarks/live-rendering.json)。

| 划分与协议 | 参考编码 | 新编码 |
| --- | ---: | ---: |
| Dev，统一阈值 0.2 | 29.91% | 24.42% |

**Dev 统一阈值 mIoU 退步**，上游式 Test bbox 定位率也从 **63.64% 降至 45.45%**；结果同时包含表中的改善项和上述退步项。上游式口径包含平滑、相对归一化与另一阈值，与原始响应固定阈值协议分别报告。Dev 被开发过程反复检查，固定 RGB 几何也可能包含评价照片。划分 ID、参数、源码/模型指纹和完整结果见 [语义证据](../reports/benchmarks/semantics.json) 与 [协议说明](semantics.md)。

## 验证方法

### 算法与接口

```powershell
$env:CUDA_VISIBLE_DEVICES = ""
$env:MINICOLMAP_TEST_GSPLAT = "0"
.\.venv\Scripts\python.exe -m pytest tests exercises -q -p no:cacheprovider --ignore=tests/support/test_gaussian_cuda.py --ignore=tests/support/test_nerf_cuda.py --ignore=tests/support/test_gsplat_native.py
.\.venv\Scripts\python.exe scripts/check_core_integration.py
.\.venv\Scripts\python.exe scripts/check_core_integration.py --noise-px 0.2
```

`tests/core` 验证几何、轨迹、地图与 BA；`tests/support` 验证数据、配置、计时、训练和后端；`tests/ui` 验证接口、取消、历史刷新与实时会话。`exercises/` 收录已完成算法的专项回归。

已保存的 CPU 回归记录使用 Windows 默认 cp936 编码、Python UTF-8 模式关闭的环境，覆盖上述 CPU 范围：**809 项通过、16 项跳过**。16 项由缺少固定版本上游源码/渲染器/压缩器的 8 项，以及 Windows 未授予符号链接权限的 8 项组成；上方显式排除的 3 个真实 CUDA 测试模块单独列示。前端记录为 **49 项通过**，TypeScript 与生产构建通过。

GPU 验证以实际 CUDA 设备、可用扩展和相应测试通过记录为依据；跨机器比较时分别记录通过、无设备跳过及其他跳过项。测试覆盖数值和工程约束，实际画质通过验证图像与指标评价。

### GPU 自检

```powershell
.\.venv\Scripts\python.exe scripts/check_render_gpu.py --output .cache/render-gpu-check.json
.\.venv\Scripts\python.exe scripts/check_gsplat_backend.py
```

### 前端与浏览器

```powershell
cd web
npm test
npm run build
node e2e/gaussian-sh-config.mjs
```

最后一项连接正在运行的本机工作台，在空闲时检查 SH、500 万数量边界、后端、导出与配置校验，不启动训练。配置表单测试关闭 WebGL；三维交互使用独立脚本。

三维相机检查可用 `npm run test:e2e:camera`；实时高斯检查先准备完成的 3DGS 历史，并在 PowerShell 指定实际任务 ID：

```powershell
$env:GSPLAT_RUN_ID = '<当前已完成的3DGS任务ID>'
npm run test:e2e:gaussian-live
node e2e/gaussian-live-perf.mjs
```

Python 链路计时在项目根目录运行，关闭其他实时会话：

```powershell
.\.venv\Scripts\python.exe scripts/check_gsplat_live.py --run-id <实际任务ID> --warmup 10 --duration 60 --output .cache/live-benchmark.json
```

`node e2e/timings.mjs` 可用 `TIMING_RUN_NAME` 指定当前 SfM 历史名称，检查阶段计时面板。部分早期浏览器脚本默认引用历史结果；在新环境运行前，准备其前置数据，并通过支持的环境变量指定本机有效 ID。`npm run test:e2e` 验证当前显卡选择、任务删除及演示；只创建并清理自己的导入与短训练副本。`npm run test:e2e:rendering` 验证可调参数和真实训练预览，`npm run test:e2e:demo` 验证已配置的独立场景。这些端到端脚本可能启动真实训练，与 CPU 回归分开执行；运行前确认无活动任务，并显式选定空闲物理卡，见 [Linux 部署与设备选择](linux-deployment.md)。
